# 架构

[English](architecture.md) | [简体中文](architecture.zh-CN.md)

## 设计目标

Late 将 **核心上下文（Central Context）视为稀缺资源**。

标准的编程智能体会将代码库扫描结果、编译器追踪信息、文件转储以及失败的补丁尝试不断累积到一个持续膨胀的执行轨迹中。随着执行噪音污染上下文窗口，模型的推理能力会显著下降。

Late 将规划与执行分离：**主编排器（Lead Orchestrator）**仅保留高层规划、架构决策以及验证后的结果。所有中间执行噪音都会被隔离在一次性的工作智能体上下文中，并在任务结束后丢弃。

## 核心组件

### 主编排器 (Lead Orchestrator)
- **角色：** 高级系统架构师、规划者和验证者。
- **能力：** 探索高层级项目结构，编写实现计划，通过待办事项（todos）追踪进度，并协调执行。
- **严格限制：**
  - 不能直接编辑文件（在物理层面上未注册 `write_file` 和 `target_edit` 工具）。
  - 拦截破坏性的 shell 操作（包括输出重定向 `>`）。
  - 被要求不得直接进行大范围的代码库扫描；将探索发现的任务委托给研究员（Researcher）。
- **子智能体调度：** 通过 `spawn_subagent`（顺序执行）或 `batch_spawn_subagents`（并发批量执行）将原子化的实现步骤分发给专门的工作智能体。

### 研究员 (Researcher)
- **角色：** 只读的代码库探索者和代码上下文研究员。
- **能力：** 使用原生搜索工具（`read_file`、`search_content`、`find_files`）和安全的 shell 命令来追踪逻辑、检查依赖关系，并梳理代码库结构。
- **上下文：** 每次调用都在一个全新的、隔离的上下文中运行。
- **输出：** 将结构化、高价值的发现结果直接返回给编排器。
- **限制：** 不能编辑文件、进行编排、创建实现计划、管理会话待办事项，或生成更多的智能体。

### 程序员 (Coder)
- **角色：** 专注于执行原子代码修改的工作智能体。
- **能力：** 使用精确的编辑工具（`target_edit`、`write_file`）和 shell 执行（`bash`）来应用更改、运行构建并执行测试套件。
- **上下文：** 在全新的、隔离的草稿区中运行，专门处理单个分配的任务。
- **输出：** 返回简明的诊断结果（确切的更改内容、测试结果或遇到的歧义）。
- **限制：** 不能进行编排、创建实现计划、管理会话待办事项，或生成更多的智能体。

## 执行流程

1. **用户请求：** 用户提交功能请求、重构或错误修复。
2. **上下文探索（可选）：** 对于非简单的任务，编排器会调用 `spawn_subagent`（类型：`researcher`）来检查代码库并报告约束条件、相关文件和代码模式。
3. **计划制定：** 编排器综合调查结果，并通过 `write_implementation_plan` 将正式的计划写入 `./implementation_plan.md`。
4. **里程碑追踪：** 编排器使用 `create_todos` 注册原子化的阶段任务。
5. **工作委托：** （获得批准后）编排器调用 `spawn_subagent`（类型：`coder`）来执行单个原子步骤，或使用 `batch_spawn_subagents` 并发执行互不依赖的独立步骤。
6. **隔离执行：** 程序员在私有上下文中检查指定文件、应用修改并运行验证命令。
7. **结构化交接：** 程序员返回所做更改、测试结果或阻塞问题的结构化摘要。其临时上下文随后被销毁。
8. **验证与推进：** 编排器评估结果，通过 `finish_todo` 将任务标记为完成，然后继续下一步。

## 为什么上下文隔离很重要

- **执行噪音累积：** 完整的文件读取、编译器诊断、代码检查工具（linters）以及失败的补丁尝试会迅速使上下文窗口饱和。
- **认知能力下降：** 实证研究表明，一旦上下文利用率超过 40–50%，长上下文模型的推理准确率最高会下降约 45% (arXiv:2601.15300)。
- **一次性草稿区：** 失败的尝试、测试日志和中间的 grep 查询仅在执行期间有用。任务完成后将它们丢弃，可防止低价值的执行历史污染模型的推理能力。
- **聚焦的核心上下文：** 编排器的上下文窗口仅包含架构意图、里程碑状态和验证后的结果。
- **突破单窗口限制：** 在本地测试中，拥有 64k 上下文预算的模型通过将执行工作分散到全新的、一次性的上下文中，完成了超过 200k tokens 的综合工程工作。

## 架构级强制执行

与那些仅通过提示词推荐或将子智能体委托设为可选的系统不同，Late 在运行时强制实施了这种分离：

- **物理工具命名空间裁剪：**
  - 写入工具（`write_file`、`target_edit`）不会注册在编排器的工具注册表中。
  - 在构建子智能体注册表时，规划和委托工具（`spawn_subagent`、`batch_spawn_subagents`、`write_implementation_plan`、`create_todos`、`list_todos`、`finish_todo`）会被省略。
- **Shell 级别的强制执行：**
  - Shell 命令会经过 AST 和策略引擎的处理。阻止 Shell 输出重定向（`>`），以防止编排器通过 shell 脚本变相写入文件。
  - 搜索命令（`grep`、`find`、`rg`）会被拦截，并指引使用能够感知 `.gitignore` 的原生搜索工具。
- **非递归的叶子工作智能体：** 子智能体不能生成其他子智能体。编排层级严格保持扁平化（深度 = 1）。
- **强制委托管道：** 由于编排器缺少修改原语，所有对代码库的修改都必须通过委托工作智能体来完成。

## 上下文与缓存策略

- **确定性且缓存稳定的前缀：** Late 避免在全局的“规划”和“构建”模式之间切换，从而在多轮交互中保留 KV 缓存的提示词前缀。在 Late 中，编排器始终处于规划状态。
- **一次性计算 vs 核心上下文：** Late 故意在临时工作智能体上消耗更多的总推理算力，以保护核心编排器的决策上下文。
- **优化指标：** Late 的优化目标是**单位核心上下文产生的最大有效工作量**，而不是最小化总的原始 token 数量。它用廉价的一次性计算换取更高质量的架构级推理。

## 规划与待办事项 (Todos)

- **计划初始化：** 在代码修改开始之前，计划会通过 `write_implementation_plan` 提交到磁盘（`implementation_plan.md`）。
- **待办事项生命周期：**
  1. `create_todos`：在计划保存后由编排器立即调用，以在会话内存中初始化按顺序执行的里程碑。
  2. `list_todos`：由编排器查询，以在多轮交互中监控整体进度。
  3. `finish_todo`：当每个工作智能体成功交付并验证一个原子步骤时，由编排器调用。
- **子智能体保护：** 待办事项的管理仅限于主编排器智能体（`id == common.MainAgentID`）。子智能体被禁止修改会话里程碑。
- **跨轮次稳定性：** 待办事项状态驻留在根编排器内存中，在子智能体终止后依然存在，从而为多步骤重构提供了稳定的支撑。

## 模型路由

- **默认配置：** 主编排器和所有工作智能体默认使用相同的模型配置。
- **混合 / 异构路由：** 可以为每种智能体类型分配独立的模型和端点（例如，将规划任务路由到能力更强的前沿推理模型，而将原子代码编辑和搜索任务路由到快速、高性价比的模型）。
- **与模型无关的后端：** 能够与任何标准的 OpenAI 兼容 API 端点（本地或远程）进行交互。

## llama.cpp 集成

- **自动发现：** 默认指向 `http://localhost:8080`。当连接到 `llama-server` 时，Late 会自动查询 `/props` 或 `/models` 以配置上下文长度，无需用户手动设置。
- **经验性 Logit 偏置（Empirical Logit Biasing）：** Late 实现了依赖于模型的 logit 抑制，该机制受 EMNLP 2025 研究启发。该研究在其评估设置中显示，冗余推理 token 可减少 27%–51%，且不会损失准确率。Late 会在采样层面对重复的自我反思 token（如 "Wait..."、"Hmm"）施加惩罚。
- **模型相关调优：** Logit 偏置映射会根据检测到的模型架构和分词器进行自适应调整。

## 流式重试策略

Late 将每次 LLM 流式调用包裹在两个相互独立的重试层级中，各自拥有独立的预算和计数器：

- **基础设施层（Infrastructure tier）：** 覆盖传输类错误（连接被拒绝/重置、超时、响应体中途断开）以及 HTTP 408/429/5xx。预算通过 `-max-stream-retries` / `LATE_MAX_STREAM_RETRIES` 控制（默认 10；`0` 或负值会完全禁用流式重试）。优先级为 CLI 标志 > 环境变量 > 内置默认值。
- **流式中断：** 响应体中途的传输故障发生在服务器已经接受请求（HTTP 200）之后——包括 HTTP/2 RST_STREAM / INTERNAL_ERROR（典型报错文本：`stream error: stream ID N; INTERNAL_ERROR; received from peer`）、GOAWAY、连接重置以及响应体被截断——因此客户端会将其包装为类型化的 `StreamInterruptedError`，并从基础设施层预算中进行重试。唯一的例外是超出 1 MB 扫描器上限（`bufio.ErrTooLong`）的 SSE 行——它会快速失败，因为重试无法缩短该行。
- **无效请求体层（Bad-body tier）：** 仅覆盖 HTTP 400，使用一个专用的小预算（3 次，常量 `DefaultMaxBadBodyRetries`；暂不支持通过命令行标志配置）。严格的 OpenAI 兼容网关（如 z.ai/GLM）在读取请求体时经常发生瞬时故障（"read body failed"），少量快速重试即可解决；而真正格式错误的请求仍会在这一小额有界预算耗尽后终止。全局禁用（`-max-stream-retries 0` 或负值）会同时关闭两个层级——包括本层级——因此全局禁用后的运行也不会再重试 HTTP 400。
- **退避（Backoff）：** 指数退避——以 500 ms 为基数逐次翻倍，上限 30 s，并叠加完全抖动（full jitter，在 `[0, cap]` 区间内均匀取值）。服务器返回的 `Retry-After` 会被作为退避下限遵守——合并后的等待时间绝不短于服务器要求的时长——并设有 5 分钟上限，以防止恶意或有缺陷的服务器挂起交互会话；等待过程始终可以取消。
- **快速失败（Fail-fast）：** 重试无法解决的错误绝不会重试：TLS 证书/信任故障（不受信任的颁发机构、主机名不匹配、无效或过期的证书链）、TLS 连接上的非 TLS 字节、不支持的 URL scheme、HTTPS 端点上的纯 HTTP、上下文取消，以及永久性的客户端错误（401/403/404）。未知错误同样会快速失败，与引入重试之前的行为完全一致。
- **计数器相互独立：** 400 的重试不会消耗基础设施层的预算，反之亦然。
- **重试状态与恢复：** 当某次尝试正在被重试时，状态行会显示为 `retry N/M after Xs backoff`——即本次失败后、下次尝试前应用的退避时长，只渲染一次且不会更新，因此并不表示实时倒计时。一个专用的 `RecoveryEvent` 会在重试后的尝试成功的瞬间宣布恢复——每个发生重试的轮次恰好触发一次——而不是等待下一个轮次的 "thinking" 状态。

当重试预算耗尽时，以下两项保证让会话仍然可用：

- **历史净化（History sanitization）：** 每次请求前会修复在工具执行中途被打断的历史——为悬空的助手 `tool_calls` 合成对应的工具结果。只有发往 API 的请求副本会被修复，已保存的历史保持不变。
- **终态 400 回滚：** 如果 API 在无效请求体重试之后仍然拒绝请求体，最后一条用户消息会被回滚，且回滚结果在所有情况下都会持久化——包括回滚导致历史为空的情况（过期的历史文件会从磁盘删除，同时保留 `.meta.json` 文件以便 `--continue` 仍能定位该会话）——使会话回到提交前的状态，而不是陷入阻塞。

## 持久化

- **根会话历史：** 编排器的对话历史持久化到磁盘上的 `<sessionsDir>/<sessionID>.json` 中，并配有用于状态恢复的 `.meta.json` 文件。该文件记录会话启动时所在的项目目录（`working_dir`），`--continue-project` 用它将恢复范围限定为当前项目——当前工作目录所在的 git 仓库根目录，不在仓库中时回退为当前工作目录本身——并通过同文件（same-file）身份检查使符号链接路径同样可以匹配。
- **可选的子智能体历史：** 执行期间，活动的子智能体上下文临时驻留在内存中。启用后，子智能体的完整会话记录会被持久化到 `<sessionsDir>/<sessionID>/subagents/<childID>.json` 以供审计和调试。
- **临时上下文 vs 磁盘审计：** 工作智能体不会将其原始上下文传回编排器；调试和事后分析依赖于磁盘上的会话记录，而不是过载的核心 KV 缓存。

## 设计权衡 (Design Tradeoffs)

- **更高的总推理开销：** 由于独立的系统提示词、上下文加载和交接，多智能体分解比单一上下文执行会消耗更多的总 token。
- **耗时增加（Wall-Clock Overhead）：** 与直接执行相比，多阶段的研究、委托和验证可能会显著增加实际运行时间（wall-clock time）。Late 有意以额外的时间和推理开销为代价，来换取更强的隔离性以及在复杂任务上持续的决策质量。
- **交接压缩风险：** 对工作智能体的执行结果进行摘要时，如果工作智能体返回的报告不完整，可能会遗漏细粒度细节。
- **目标工作负载：** 该架构专门针对复杂、涉及多文件或长时程任务进行了优化。对于简单的单行修改，编排带来的额外开销是不必要的。
